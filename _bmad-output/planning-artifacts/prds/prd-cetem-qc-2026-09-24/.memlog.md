- (decision) User clarification: 1. Obsolete audit approval Remove the obsolete 'validate/reject employee work' action, state, and associated report fields. The latest workflow should not contain a separate approval of the employee's work after submission. After submission: - the submitted measurements are immutable; - the Responsable reviews the audit results; - the Responsable selects/adds insights; - the Responsable confirms the summary; - the Responsable makes the machine conformity decision; - the Responsable finalizes/designates the official report. For DR-005, retain actor/date traceability for: - audit submission; - summary confirmation; - machine conformity decision; - official report finalization/designation. Do not create a separate 'audit approval' event.
- (decision) User clarification: 2. Employee accounts and task initiation For the PoV, implement the account operations necessary to demonstrate the workflow: - Responsable creates an employee account; - employee receives/uses initial credentials; - employee authenticates; - Responsable can activate/deactivate the employee. Do not expand the PoV into complete identity administration beyond what is necessary for the demonstration. An Employé must NOT initiate an unassigned control in Phase 1. Controls originate from tasks assigned by the Responsable. If an employee is deactivated: - no new login or new work is allowed; - existing tasks and historical audit data must not be deleted; - unfinished assigned tasks remain visible to the Responsable for reassignment/handling. The exact reassignment behavior can be finalized during detailed workflow design.
- (decision) User clarification: 3. Offline submission and conflicts For the PoV, treat an audit as being actively edited from one tablet at a time. Full multi-device collaborative synchronization is out of scope. The employee may complete the audit offline and request submission while offline. However, offline 'submission' should be represented locally as pending synchronization. Server-side submission becomes authoritative only after successful synchronization/server acceptance. Until server acceptance, the local data must remain preserved. Once server acceptance succeeds: - the audit becomes submitted; - measurements become immutable. If synchronization detects that the server version has changed, do not silently overwrite either version. For the PoV: - preserve the local draft; - warn the user about the conflict; - require reload/reconciliation before synchronization continues. Automatic field-level merge is not required for Phase 1.
- (decision) User clarification: 4. Offline access and unsynchronized drafts This remains partially unresolved. For the PoV: - unsynchronized drafts must be stored securely on the tablet; - session expiry/logout must not silently delete unsynchronized audit data; - account deactivation must prevent future authorized synchronization/work once the server learns of the deactivation. The exact permitted offline authentication duration/session expiry remains an unresolved security configuration decision and should be recorded as such in the PRD rather than invented. Logout behavior for unsynchronized drafts also requires an explicit security/UX decision.
- (decision) User clarification: 5. Correcting submitted measurements Submitted measurements remain immutable. If a material measurement error is discovered after server-side submission, the submitted audit must not be edited in place. A new control/audit must be performed. The replacement should be LINKED to the original audit/task for traceability, while remaining an independent audit record with its own measurements, timestamps, calculations and outcome. The original remains preserved as historical evidence. Treat the PoV D-12 wording 'independent' as meaning an independent record, not an untraceable record.
- (decision) User clarification: 6. Insight timing and empty selections The Employé should see: - entered measurements; - calculated values; - individual tolerance results. The deterministic insight proposal workflow is for the Responsable after submission. FR-042 should therefore not be interpreted as requiring the employee to perform insight review offline. Offline functionality applies to the field audit workflow and the calculations/tolerance feedback necessary to perform it. For an all-normal audit, zero selected/added insights is valid. The Responsable may confirm a summary with no selected insight. The generated/manual summary may simply describe that the control results are within the applicable tolerances. Do not require creation of an artificial insight just to enable finalization.
- (decision) User clarification: 7. Approved business rules Do not invent formulas, thresholds, inclusivity rules, rounding, N.A. behavior, kVmax/K2/linearity rules, or mandatory measurement fields. These require the approved CETEM BH calculation/control catalogue and reference dataset. Keep them as unresolved dependencies if the approved source is not currently present in docs/product. The application may automatically calculate: - derived values; - individual tolerance verdicts; - deterministic observations/insights where the rule is explicitly defined. Do NOT introduce an automatic overall machine-conformity decision. Final machine conformity remains a human decision by the Responsable.
- (decision) User clarification: 8. Official report and signature For the PoV, designating/finalizing the official report completes the software workflow. The report can follow either documented path: - system-generated Word report; or - manually produced PDF uploaded by the Responsable. Handwritten signature happens after the software workflow. Do not require uploading a signed scan for Phase 1 unless this is later explicitly approved as a requirement. The exact approved report template, mandatory report fields/provenance fields, and maximum PDF upload size remain unresolved dependencies and must be flagged in the PRD. The report should nevertheless preserve traceability to the relevant task/audit, Responsable, conformity decision and finalization date.
- (decision) User clarification: 9. AI failure behavior AI availability must not block completion of the control workflow. If AI summary generation fails: - the Responsable may retry generation; - the Responsable must also be able to write the summary manually and continue. The manually entered summary follows the same confirmation requirement as an AI-generated summary. AI remains an assistance mechanism, not a decision authority or critical workflow dependency.
- (decision) User clarification: 10. Evidence attachments Do not include general audit/insight evidence attachments in the Phase 1 PoV unless an existing confirmed requirement explicitly requires them. Keep this outside the PoV scope for now. The official report upload is separate and remains in scope. If evidence attachments are required later, file types, size limits, storage, security and association rules must be specified before implementation.
