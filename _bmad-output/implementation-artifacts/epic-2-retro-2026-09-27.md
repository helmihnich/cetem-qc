## What went well

- **Controlled bootstrap:** first-Responsable creation is CLI-only and out-of-band. No public bootstrap/signup route or Admin role is introduced. It generates a cryptographically random temporary credential, persists only a salted scrypt hash, sets `must_change_password`, and prints the credential once for controlled handover. A PostgreSQL advisory transaction lock serializes single-use bootstrap attempts (`apps/api/src/scripts/bootstrap-responsable.ts`; `apps/api/src/modules/identity-auth/bootstrap.ts:10-36`; `apps/api/src/modules/identity-auth/password.ts:7-25`; `apps/api/src/modules/identity-auth/bootstrap.test.ts:21-47`).
- **Authentication protections:** login normalizes email, reuses the persisted scrypt format, returns a generic French failure for unknown, wrong-password, and inactive-account cases, and performs dummy-hash verification for unknown email (`apps/api/src/modules/identity-auth/authentication.ts:8-10,54-68`; `apps/api/src/modules/identity-auth/password.ts`; `apps/api/src/modules/identity-auth/authentication.test.ts:93-123`).
- **Session handling:** bearer tokens are opaque random values; only SHA-256 digests are stored. The server enforces an eight-hour expiry and checks current active account state on session inspection (`apps/api/src/modules/identity-auth/sessions.ts:8-45`; `apps/api/src/db/migrations/0003_identity_sessions.sql`).
- **Temporary-access boundary:** the route guard defaults protected routes to requiring an active session, and while `must_change_password` is true it permits only session inspection, logout, and password replacement. Password replacement rejects reuse of the temporary credential, then atomically updates the password hash, clears the flag, revokes prior sessions, and inserts a replacement session in one transaction (`apps/api/src/index.ts:26-43,103-141`; `apps/api/src/modules/identity-auth/authentication.ts:67-91`; `apps/api/src/modules/identity-auth/sessions.ts:64-93`).
- **Failure-safe lifecycle:** transaction tests preserve the original failure across rollback/release failures. Route tests verify positive and negative outcomes, safe error responses, session revocation, deactivation/expiry, and replacement rollback. Shutdown explicitly awaits HTTP server closure and pool shutdown (`apps/api/src/db/transaction.test.ts`; `apps/api/src/authentication-routes.test.ts`; `apps/api/src/shutdown.test.ts`; `apps/api/src/index.ts:146-190`).
- **Offline policy remains distinct:** the eight-hour server session lifetime is documented separately from the seven-day OD-01 mobile authorization window (`apps/api/src/db/README.md:13-15`; architecture spine AD-5; `epics.md:83`).

## What caused review rework

- **OpenAPI lagged the implementation.** Authentication/session routes were added before the contract fully represented them, and the session endpoints initially omitted the actual `500` error outcomes. That created a gap between the HTTP behavior and the API's declared source of truth. The current contract declares authentication, session inspection, logout, password replacement, and their actual success/validation/authentication/internal-error responses (`packages/types/openapi/cetem-qc-v1.yaml:33-138`). **Disposition: fixed.**
- **Resource lifetime was initially wrong for a server.** Creating a PostgreSQL pool per request risks resource exhaustion; it was changed to lazy application-level reuse and explicit shutdown awaiting pool closure. Current `createApp` keeps a shared pool and the process shutdown path awaits `closeDatabase` (`apps/api/src/index.ts:14-16,146-190`). **Disposition: fixed.**
- **Request-shape tests did not prove route outcomes.** Malformed-request tests alone could not establish successful authentication, generic credential rejection, temporary-session restrictions, logout, deactivation, or rollback behavior. The route suite now exercises those paths and internal-error sanitization (`apps/api/src/authentication-routes.test.ts`). **Disposition: fixed; make outcome tests the default.**
- **Rollback test infrastructure initially did not model database transactions.** A mock that mutates persistent state immediately cannot prove rollback restores atomic state. The authentication fake pool now snapshots account/session state at `BEGIN`, restores it at `ROLLBACK`, and publishes it at `COMMIT`, with a failure test that verifies all pre-change state remains intact (`apps/api/src/modules/identity-auth/authentication.test.ts:22-82,152-173`; route-level rollback case in `authentication-routes.test.ts`). **Disposition: corrected; reusable test-fixture rule.**

## Findings and reusable security rules

### Architecture and aggregate view

- **Architecture delta — consistent with the spine.** Authentication is owned by `identity-auth`; persistence is PostgreSQL; the CLI bootstrap is controlled operations; Express is the HTTP boundary. No public registration or application-admin workflow exists in the route map. Sources: architecture spine AD-3/6; `apps/api/src/index.ts`; `apps/api/src/scripts/bootstrap-responsable.ts`; `apps/api/src/modules/identity-auth/`.
- **Shared resource lifetime — fixed, retain as a standing rule.** One PostgreSQL pool is reused by the application and explicitly closed during graceful shutdown. Do not instantiate shared connections, clients, or providers per request. Source: `apps/api/src/index.ts:14-16,146-190`.
- **Protected-route activation policy — centralized, retain as default-deny.** `must_change_password` is enforced in the shared session middleware before future handlers are reached. New protected routes must remain behind that middleware; activation exceptions must be explicit and tested. Source: `apps/api/src/index.ts:26-43,103-141`.

### Security rules to standardize

1. Bootstrap and privileged initial setup use controlled operator paths, never public signup/admin endpoints. Generated credentials are high entropy, returned once through a controlled channel, and never logged or stored in recoverable form. Source: bootstrap CLI/module and `bootstrap.test.ts`.
2. Store passwords using salted adaptive hashing; use one generic public authentication failure for unknown, incorrect, and inactive credentials. Perform equivalent expensive verification for unknown identifiers to reduce timing differences, while recognizing this does not make timing perfectly constant. Source: `authentication.ts:8-10,54-68`; `password.ts`; authentication tests.
3. Issue opaque high-entropy bearer tokens and persist only a digest. Re-read authoritative account activation and session status for each protected request; never trust a client-supplied role or cached active flag. Source: `sessions.ts:18-45`; `authentication-routes.test.ts`.
4. Make temporary-credential restrictions central middleware policy so newly added protected operations are restricted by default. Allow only enumerated activation/session operations until replacement. Source: `index.ts:26-43`.
5. A credential replacement that changes account state and sessions is a single transaction. Preserve old credentials/session usability if any write fails. Source: `authentication.ts:67-91`; `sessions.ts:64-93`; rollback tests.
6. Keep offline authorization lifetime separate from server session expiry and test each policy in its owning layer. Source: `db/README.md:13-15`; architecture AD-5; OD-01 in `epics.md:83`.

### API-contract rules

- Define every HTTP operation in OpenAPI before or alongside its handler. Include request/response schemas and all implemented status codes, including internal `500` outcomes. The initial omissions of authentication routes and session `500`s demonstrate why handlers alone are not the full API change. Current contract source: `packages/types/openapi/cetem-qc-v1.yaml:33-138`.
- In the same story, verify generated DTOs, Zod runtime schemas, and typed client behavior remain aligned to the contract; run the drift check after edits. Epic 1 established this check in `packages/types/scripts/check-generated.mjs` and `package.json`'s `contracts:check`.
- Test both contract-level malformed input and route-level positive/negative outcomes. A schema parsing test cannot establish that authorization, database outcomes, or error status mapping behave correctly. Sources: `apps/api/src/authentication-routes.test.ts`; `packages/schemas/src/api/v1.test.ts`.

### Transaction, session, and testing lessons

- Any operation with multiple authoritative writes needs a rollback test proving state restoration after a later write fails. Its fake database must model `BEGIN`/`COMMIT`/`ROLLBACK` semantics rather than merely record SQL. Sources: `authentication.test.ts:22-82,152-173`; `transaction.test.ts`.
- If correctness depends on uniqueness, single-use credentials, or one-winner behavior, test the concurrency invariant. Bootstrap does this by acquiring the advisory lock before checking/inserting (`bootstrap.ts:21-28`; `bootstrap.test.ts`). Future account creation should similarly exercise concurrent duplicate email/single-use constraints at the appropriate database boundary.
- Exercise protected operations through direct HTTP/API requests, not only through UI assumptions. Test anonymous access, activation-only access, deactivated accounts, expired/revoked sessions, and role/scope denials as routes are introduced. Epic 2's operational test route proves the guard behavior; Epic 3 must prove own-team authorization against direct API calls.
- Tests currently run directly with Node/tsx, but `apps/api/package.json` provides no test script (`apps/api/package.json:4-13`). This makes repeatable discoverability a process gap, not evidence that tests are failing.
