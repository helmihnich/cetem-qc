## Findings

### What went well

- **Authorization stayed server-authoritative.** Responsable operations derive team scope from the authenticated account, and employee reads predicate on the authenticated employee’s assignment. Direct API tests exercise role and scope denials; PostgreSQL tests exercise the production SQL (`apps/api/src/modules/tasks/tasks.ts`, task queries and `createAssignedTask`; `apps/api/src/index.ts`, protected task routes; `apps/api/src/employee-task-routes.test.ts`; `apps/api/src/modules/tasks/employee-tasks.postgres.test.ts`). The own-team and assignment-level boundaries remain distinct.
- **PostgreSQL covered behavior mocks cannot establish.** Story 4.1’s regression exercised eligible assignment, atomic task/assignment persistence, and rollback. Story 4.2’s final migration/list test seeded migrations 0001–0006 and pre-existing data, applied the real 0007 migration, and passed against PostgreSQL 16 with zero skips. The full API suite passed 55/55 with zero skips in that final Story 4.2 run (`spec-4-2-review-the-operational-task-list.md`, “Final Fresh-Context Review”). Story 4.3’s final run reports its employee assignment integration among a 57/57 API suite and a separate 5/5 PostgreSQL integration run with zero skips (`spec-4-3-make-assigned-work-visible-in-app.md`, “Final verification”).
- **Contract work followed the established path.** The task operations were added to OpenAPI, generated types, Zod schemas, typed client, and runtime routes; generation/drift checks and schema tests are recorded as passing. Story 4.3’s final fresh-context review added six behavioral client tests for list/detail paths, GET methods, bearer headers, encoded IDs, strict response parsing, and 404/500 errors (`spec-4-3-make-assigned-work-visible-in-app.md`, lines 125–127; `packages/api-client/src/v1.test.ts`).
- **The interfaces use French and keep the intended role boundaries.** Story 4.2 stays in the Responsable web experience; Story 4.3 adds a French Employé mobile list and read-only task overview. It does not add local drafts, field entry, calculations, synchronization, submission, or email claims (`epic-4-context.md`; Story 4.3 spec, “Boundaries & Constraints” and “Implementation Notes”).
- **Review caught and closed meaningful omissions.** Story 4.2 now labels an inactive assignee without changing its six-field response contract, and preserves the historical assignment. Story 4.3 now invalidates stale detail responses when another task is selected or the user returns to the list. The generation-counter implementation has overlapping-response and invalidation tests (`spec-4-2-review-the-operational-task-list.md`, lines 83–101; `spec-4-3-make-assigned-work-visible-in-app.md`, lines 109–111; `apps/mobile/employee-task-detail-state.ts`; its test file).

### Aggregate views and spec reconciliation

- **Architecture delta:** the changed surfaces continue the modular monolith and dependency direction in AD-1/AD-2. API modules own task queries and authorization; apps consume shared contracts; Story 4.3 adds no migration and keeps read-only task data in component memory (`ARCHITECTURE-SPINE.md`, AD-1, AD-2, AD-3; Story 4.3 spec, “Implementation Notes”). No new cross-app dependency or duplicate task store was found in the inspected changes.
- **Duplication and size:** no reliable whole-range churn ranking was available because `git_evidence.py` could not pass Git’s safe-directory check. Inspection of changed task/API/mobile surfaces found no demonstrated new god-class or duplicated authorization implementation; no size verdict is claimed from the missing ranking.
- **Pattern divergence:** the PostgreSQL, strict-schema, API route, no-store, and French-copy patterns follow existing project conventions. One cross-story UI integration gap remains: the Responsable task list fetches once on mount, while successful task creation does not refresh it. A task created after initial page load is absent from the visible list until a page reload. This is a non-blocking defect spanning Stories 4.1 and 4.2 (`apps/web/src/app/page.tsx`, task-list/task-creation composition; `apps/web/src/app/task-list.tsx`, mount-only `loadTasks`; `apps/web/src/app/task-creation.tsx`, successful submit path). Proposed remediation is tracked below; no code was changed here.
- **Input contract edge:** the create-task Zod schema trims establishment before requiring non-empty text, while OpenAPI only declares `minLength: 1`; a whitespace-only value is rejected at runtime but allowed by the published schema (`packages/schemas/src/api/v1.ts`, `createTaskRequestSchema`; `packages/types/openapi/cetem-qc-v1.yaml`, `CreateTaskRequest`). Also, establishment/service schemas accept U+0000 even though PostgreSQL text cannot store it, so such a direct API request can reach the database and become a 500 (`packages/schemas/src/api/v1.ts`; `apps/api/src/modules/tasks/tasks.ts`, parameterized task insert; `apps/api/src/index.ts`, generic create failure response). These are bounded, non-blocking input/contract defects. Proposed remediation is tracked below.
- **Spec reconciliation:** Story 4.3 meets the visibility boundary without implementing Epic 5 field work. Story 4.1/4.2/4.3 behavior otherwise matches the declared task and access criteria. Fresh diff review suggestions to add ordering, pagination, time-of-day display, or list-row task type were rejected because no such behavior is required by the approved story/UX contract. Physical-device connectivity was documented as an environment limitation, not misrepresented as verified.

### Accepted Epic 5 engineering rules

1. Define every HTTP operation OpenAPI-first and keep OpenAPI, generated types, Zod, typed client, and Express behavior aligned within the same story.
2. Add behavioral tests for every new typed API-client method: versioned path, HTTP method, authentication, request serialization, successful response parsing, and contract-shaped errors.
3. Enforce role, team, and assignment scope at the API independently of UI restrictions. Preserve server authority and non-disclosing authorization failures.
4. Use production PostgreSQL for authorization predicates, transaction/rollback behavior, and migration semantics. Migration tests must seed old migrations and pre-existing data, apply the new migration, then assert results. Final verification has no unintended skipped PostgreSQL tests.
5. Test asynchronous mobile behavior with overlapping/out-of-order requests wherever navigation can change the active entity. Entity-detail requests that can overlap must ignore stale results.
6. Test local persistence and lifecycle behavior: durable commit acknowledgments, save failure retaining the previous version, restart/reload recovery, explicit delete confirmation, no silent overwrite, and logout/expiry/deactivation access rules.
7. Test critical rendered UI flows as well as state helpers and API routes. For each story, include the real user-visible boundary relevant to that behavior.
8. Before review, run the story’s unit/state and persistence tests, direct API authorization and PostgreSQL integrations as applicable, contract generation/check, boundary tests/checker, workspace typechecks, builds, relevant Expo Android/iOS exports, and `git diff --check`. Record Expo exports as JavaScript bundling only; they do not prove a native build, installation, device launch, native-module behavior, or live device connectivity.
9. Keep each story within its approved scope. Do not pull in later calculation, synchronization, submission, or business rules unless the authoritative story requires them.
