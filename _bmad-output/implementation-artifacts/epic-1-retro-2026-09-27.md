### Review and verification findings

- **Story 1.1 runtime baseline — resolved.** Initial validation used Node 22.18.0 while the architecture baseline is Node 24.21.0. The recorded validation notes explain that Node 22 met then-current Expo/Next minimums, and the implementation subsequently pinned/documented 24.21.0 in `.nvmrc`, root `package.json`, and README. This was a useful validation-environment discrepancy, not an unresolved acceptance defect (`spec-1-1...md:58`; its review triage at `:65-74`; root `package.json:5-7`).
- **Story 1.1 host binding and API construction — defer.** The development API's loopback binding limits physical-device/container access, and its entry point starts listening on import. These were explicitly deferred because the skeleton story did not require cross-device calls or an app factory. Revisit when API behavior needs device access or direct app-level tests (`spec-1-1...md:71,74`; `_bmad-output/implementation-artifacts/deferred-work.md`).
- **Story 1.2 contract drift — fixed.** OpenAPI and runtime/generated representations could disagree; generated artifact verification and focused schema tests now cover stale output and key runtime cases (`spec-1-2...md:89-92`; `packages/types/scripts/check-generated.mjs`; `packages/schemas/src/api/v1.test.ts`).
- **Story 1.2 dependency/import boundaries — fixed after review iterations.** Dependency checks now include regular, development, peer, and optional dependency declarations; source scanning catches cross-app imports, including mobile root entry cases; ownership checks reject direct cross-module persistence access. The story records focused regression tests and successful checker execution (`spec-1-2...md:69-86`; `scripts/check-boundaries.ts`; `scripts/check-boundaries.test.ts`).
- **Story 1.2 checker confidence — process lesson.** A passing boundary checker was insufficient until the cases it claimed to enforce were independently tested. The regression tests are the evidence that closed the review gaps (`spec-1-2...md:72-86`).
- **Story 1.3 transaction failure semantics — resolved.** Tests prove rollback and release failures do not replace the callback's original error, while cleanup errors are reported and release is attempted (`apps/api/src/db/transaction.ts:10-39`; `apps/api/src/db/transaction.test.ts:6-142`).
- **Story 1.3 migration rerun coverage — defer, nonblocking.** The migration runner checks `schema_migrations` under an advisory transaction lock before executing each migration. Existing focused tests cover serialization during migration table initialization but no direct test exercises rerunning an already-applied migration (`apps/api/src/db/migrate.ts:11-31`; `apps/api/src/db/migrate.test.ts:6-57`). This is a test gap, not evidence of a current defect; no live PostgreSQL integration test was required by the story criteria (`epics.md:202-216`).

This prevents checking its recorded review disposition and validation notes. No story is reopened based on this documentation gap.

## Reusable engineering rules

1. A source-of-truth claim needs a drift check: generated contracts must be compared to their source, not merely compiled.
2. Boundary enforcement must account for every dependency edge and every source entrypoint, including package peers/optional dependencies and app root files.
3. Every checker needs focused tests for bypasses; a passing checker run alone does not validate its coverage.
4. For transactional helpers, preserve the primary operation error through rollback, logging, and release failures; test each failure combination.
5. Concurrency protection belongs around the check-and-apply decision, using a database lock in the same transaction as the migration.
6. Capture the runtime actually used for validation and compare it with the pinned project baseline; if they differ, state why and validate against the declared toolchain before relying on the result.
7. Complete each story's implementation artifact with review outcomes and verification evidence before marking it done.
