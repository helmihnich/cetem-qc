### Security lessons — rules to carry forward

1. **The API is the authorization authority.** UI hiding and the web proxy are conveniences; each API route must independently enforce authentication, role, and resource scope (`apps/api/src/index.ts`, lines 36–53 and 140–223; architecture spine, AD-3 / server authorization rule).
2. **Derive team scope on the server.** Resolve the Responsable’s team from the authenticated account; do not accept a team ID from the browser. Current create/status commands take the authenticated Responsable account ID and derive team through `identity_teams` (`employee-credentials.ts`, lines 42–49 and 89–96).
3. **Direct API authorization tests are mandatory.** Cover anonymous requests, wrong role, cross-team access, inactive users, and invalid state through HTTP routes, not only UI or service methods (`apps/api/src/employee-routes.test.ts`; architecture spine server-authorization rule).
4. **Every authenticated cookie mutation uses the shared same-origin/CSRF guard.** Require an explicit matching Origin before forwarding any bearer token; keep all new mutation routes on the same reusable helper (`apps/web/src/app/api/csrf.ts`; mutation route imports and `route.test.ts`, lines 105–133).
5. **Bearer tokens stay server-side/HttpOnly.** The browser sees an HttpOnly session cookie; the cookie bridge forwards the token to the API and never exposes it in JSON (`apps/web/src/app/api/session/route.ts`; session route tests, lines 17–33).
6. **Evaluate active account state during authorization.** Existing sessions must stop authorizing protected server requests after deactivation; reactivation restores eligibility only through a fresh active-state check (`apps/api/src/modules/identity-auth/sessions.ts`, lines 32–46; `apps/api/src/modules/team-access/employee-credentials.postgres.test.ts`, lines 165–205).
7. **Test security behavior at HTTP boundaries as well as service level.** Exercise cookie/origin handling, API role checks, status mappings, and no-forward/no-mutation denial behavior at routes (`apps/web/src/app/api/session/route.test.ts`; `apps/api/src/employee-routes.test.ts`).

### Database and testing lessons

- Use real PostgreSQL tests whenever behavior depends on PostgreSQL constraints, transactions, locks, or SQL predicates. Fake repository/pool tests verify application decisions and query intent; they do not prove actual production SQL or driver error metadata.
- Assert the exact constraint/error mapping observed from PostgreSQL. Keep the production constraint name and the public API error mapping aligned and regression-tested.
- Add concurrency tests for uniqueness and single-use/eligibility operations where competing requests could both pass a pre-check. Story 3.2’s canonical-email concurrency test is the model (`employee-credentials.postgres.test.ts`, lines 11–72).
- Test rollback for multi-write operations so a later failure leaves no partial account, membership, credential, or session state. Use PostgreSQL for transaction guarantees that mocks cannot establish.
- Isolate integration schemas, pools, and environment variables. Explicitly injected test dependencies must take precedence over ambient integration-test configuration. A fixture-selection error is test infrastructure, not evidence of a production bug.
- Test migrations against both empty and populated schemas, especially when adding membership/backfill behavior. Story 3.1’s review identified the populated-upgrade path, while its recorded validation had no live PostgreSQL upgrade run (`story-3-1-review-findings-2026-09-27.md`).

### Contract lessons

Continue the established sequence: OpenAPI first → generated types → Zod request/response schemas → typed client → runtime handlers → contract drift check. Keep every actual runtime error/status response represented in OpenAPI; route behavior and typed contract must not diverge. This follows Epic 1’s contract foundation and Epic 2’s recorded response-status lesson (`epic-1-retro-2026-09-27.md`, “API contract” findings; `epic-2-retro-2026-09-27.md`, “API-contract rules”).

### Epic 4 readiness rules — Task Creation and Assignment

1. Reuse the existing Responsable/team authorization pattern and server-derived team scope.
2. Assignment candidates must be active, same-team Employés. A Responsable must never be assignable as an Employé.
3. Enforce candidate and task scope in the API for direct calls, independently of the UI.
4. Deactivated employees cannot receive new assignments. Deactivation must not automatically reassign existing work; follow the resolved task lifecycle policy when later recovery behavior is implemented (`epics.md`, lines 310–316 and 651–663; architecture spine deactivation rule).
5. Use a PostgreSQL transaction for task and assignment writes that must succeed or fail together.
6. Add PostgreSQL-backed tests for the production assignment predicates and transactional outcomes. Include cross-team, inactive employee, wrong-role, and relevant concurrency cases.
7. Protect cookie-authenticated web mutations with the shared same-origin guard and test that rejected requests are not forwarded.
8. Keep the interface in French and follow the existing UX artifacts.
9. Phase 1 has no email/SMS notification or delivery tracking (`DESIGN.md`, lines 159 and 183; `EXPERIENCE.md`, notification/credential handover scope).
10. Keep Epic 4 to task creation, assignment, and its operational task list. Do not pull in Epic 5 mobile field-work/offline behavior (`epics.md`, Epic 4 and Epic 5 sections; `EXPERIENCE.md`, mobile flows).
