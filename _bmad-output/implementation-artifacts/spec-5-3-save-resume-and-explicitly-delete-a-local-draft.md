# Story 5.3 implementation spec

## Goal and authoritative acceptance criteria

Implement only the local editable-draft lifecycle required by Story 5.3. A draft save remains a local draft: **Saved locally != synchronized != submitted**. No form field catalogue or business rules are introduced.

Authoritative acceptance criteria, transcribed from `epics.md`:

1. **Given** an editable pre-submission draft and a working local datastore
   **When** meaningful changes occur, the user navigates sections or selects Enregistrer
   **Then** autosave and explicit save persist transactionally and acknowledge only after durable local commit
   **And** latest saved work survives normal app/device process restart without network; a failed save retains the last successful version and clearly reports that newer edits are not saved
   **And** explicit draft deletion requires confirmation; pending submission snapshots cannot be deleted through the draft-delete action.

Traceability: FR-019, NFR-001, NFR-004, AD-5, UX-DR2 (`button-primary`, `button-destructive`, `confirmation-dialog`, `loading-state`), UX-DR4, UX-DR13.

## Planning choices

These are implementation proposals for checkpoint approval, not changes to product code.

### Draft identity and task relationship

- Draft has a stable random `draftId`; task identity is the assigned server task ID. Identity key is the authenticated employee account ID from Story 5.2. These form the local uniqueness scope.
- **Persistence invariant: one active local editable draft per employee account + task** for the current PoV. Reopening the task resumes that draft. Correction flows, replacement controls, conflict revisions, and pending-submission snapshots retain separate lifecycle semantics and are not ordinary editable drafts.
- Draft ID, account ID, task ID, schema version, created/updated timestamps, monotonically increasing revision, and opaque payload are stored. No fabricated audit/form fields, units, requiredness, validation, formulas, tolerances or section structure.
- Minimal payload is opaque versioned JSON (initially an empty generic object or only generic user-edited opaque data needed by the story). 5.4 must migrate/replace the representation only when its approved catalogue exists; unknown future schema versions fail closed and preserve bytes for recovery.

### Persistence and encryption

- Use Expo SDK 57 compatible `expo-sqlite ~57.0.3` with SQLCipher enabled through its config plugin. The key is a cryptographically random 256-bit value generated by `expo-crypto` and held in platform SecureStore through the existing adapter; do not store keys beside the database. Expo SDK 57 documents Android/iOS support, durable persistence, exclusive transactions, schema `user_version`, and SQLCipher configuration. Native encryption behavior still requires a native build/device check.
- Scope records and lookup indexes by account + task. Encrypt database content at rest; avoid sensitive payload in logs, analytics, filenames or user-facing errors. Story 5.2 `readProtectedPayload`/authorization checks remain the access gate; do not use generic storage access as authorization.
- A durable commit means transaction commit completed successfully. UI displays Saving until completion and Saved locally only after commit. Never display synchronization or submission state from this result.
- Atomic save: write a complete new revision inside a database transaction and advance the current revision pointer in that same transaction. On rollback or I/O error, retain prior committed revision and show that newer edits are not saved. No truncate-then-rewrite in-place file operations.
- Prefer a retained previous committed revision until the next commit is known good. SQLite transaction rollback protects the prior record; corruption at DB/page level must fail closed and preserve the database file for controlled recovery rather than silently reinitialize/delete. Surface a generic recoverable storage error without exposing contents. Automated repair/recovery or data export is outside this story.

### Save, resume and delete lifecycle

- Create draft lazily on first meaningful edit or explicit save for an eligible task. Do not materialize a submitted/pending snapshot as an editable draft.
- Autosave after meaningful changes and section navigation, with debounce duration an implementation detail. Explicit Enregistrer flushes the latest in-memory draft immediately. Serialize or revision-guard asynchronous writes so stale completions cannot replace newer edits; acknowledgement corresponds to the committed revision.
- Resume looks up the account/task draft after authorization; hydrate the latest committed revision after process remount/restart without network. UI-only focus, open section, in-flight input composition and save spinner are transient state, not durable draft unless confirmed as content changes.
- Draft delete action presents French confirmation identifying the consequence. Cancel changes nothing. Confirm deletes only the editable local draft for the active account/task transactionally. Pending submission snapshots use a separate store/state and are not addressable by this delete operation; reject attempts by type/state guard. No implicit delete on logout, expiry, deactivation, failed save, migration or corruption.
- A failed deletion leaves the record intact and reports failure. Authorization closing during an async save/delete cancels or invalidates access; it never deletes data. If a durable write already committed before lock, retain the encrypted record and block subsequent reads until authorized.

## Story 5.2 authorization integration

- Before list/read/create/update/delete, evaluate the existing offline authorization for the current account using the 5.2 service. Never infer authorization from cached user UI state alone.
- Identity binding uses account ID in both storage key/record ownership and the 5.2 grant. Account switch, logout, expired grant, or known deactivation prevents draft read/write/delete. Successful online authentication only restores access according to the current 5.2 grant and server authorization. Transient network loss, app restart and ordinary server-token expiry do not reset the seven-day window.
- All lock conditions preserve encrypted database records. Logout is a lock, not a delete. Deactivated tablet-only work remains inaccessible to the employee and is not claimed synchronized; administrative recovery stays outside this story.
- Recheck authorization at operation boundaries and after awaited storage work before returning plaintext to UI. Avoid stale async completions repopulating the screen after account/task navigation or lock; use operation generations/cancellation tokens.

## Failure, rollback and corruption

- Database unavailable/full, transaction failure, secure-key unavailable, unsupported schema, malformed record, or authentication failure => fail closed; no success acknowledgement. Keep last known good committed revision. Clearly distinguish unsaved newer in-memory edits from Saved locally.
- Do not silently recreate an empty database over an existing unreadable store. Preserve encrypted source and surface a retry/support path without leaking protected data. Any future repair must be explicit and preserve originals.
- Protect writes against interruption with SQLite atomic transactions, schema migration transaction, and revision checks. A stale operation must not overwrite a newer revision. Concurrent save and delete are ordered by repository serialization/revision guard; delete confirmation is tied to the selected draft revision so stale confirmation cannot delete a replacement draft.

## Test strategy

- Repository transaction tests: create, save, revise, commit acknowledgement only after durable completion; injected failure leaves prior version intact; atomic rollback and simulated interruption; reopen adapter after remount; delete confirmed vs cancelled; delete failure retains record.
- App rendered-flow tests: first edit creates draft; meaningful change/autosave; explicit save flush; status reads Saving/Saved locally/Save failed; resume after remount; edit-save again; explicit French delete confirmation and outcome; no sync/submission implication.
- Isolation: two identities cannot list/read/overwrite/delete each other's records; task scopes remain separate; stale task/account request completion cannot hydrate active view.
- 5.2 integration: valid offline grant permits local access; transient network/restart does not reset authorization; logout/expiry/deactivation blocks read/write/delete and preserves encrypted bytes; successful authorized reauthentication restores only that identity's access.
- Security/storage: database content encrypted at rest, key material absent from DB; malformed/corrupt/unknown-version data fails closed and is preserved; SecureStore/key/database failure produces no false success.
- Race cases: overlapping saves complete out of order; save racing lock, task switch and delete; stale delete confirmation cannot remove a newer draft; prior good revision survives failed replacement.
- Cover that submitted/pending snapshots are unreachable to the draft-delete operation.

## Explicit out of scope

- Story 5.4 field catalogue, sections, measurement values, units, requiredness, validation, calculations, tolerances or CETEM BH business rules.
- Story 5.5 full offline editing of synchronized tasks unless required by its own authoritative story.
- Synchronization, outbox, transfer status, submission, pending-submission state, conflict resolution, server changes or claims of synchronization/submission.
- Calculations, insights, AI, conformity, reports, administrative recovery, multi-device collaboration, branching/multiple drafts per task, backup/export or automated corruption repair.

## Resolved checkpoint decisions and remaining limits

- Draft cardinality is approved as at most one active editable draft per employee account/task; other lifecycle records remain out of this model.
- `expo-sqlite ~57.0.3` / SQLCipher and `expo-crypto ~57.0.3` were selected after checking the installed Expo 57.0.25 / React Native 0.86.3 toolchain and SDK 57 official docs. No bare React Native transition or plaintext fallback was added.
- Debounce remains an implementation detail; current autosave debounce is 500 ms. Generic content remains opaque and does not introduce measurement field definitions.
- Native keychain/keystore and SQLCipher behavior has not been verified by the JavaScript test runner or exports.

## Review Triage Log

| Review finding | Verdict and evidence |
|---|---|
| Blind: Temporary key removal could make an existing encrypted DB irrecoverable. | **false** — The failure path closes but does not delete or reset the database; with the original key already absent, that database was already unreadable. The temporary generated key is removed on init failure. |
| Blind: `PRAGMA key` may run too late after `openDatabaseAsync`. | **false** — Expo SDK 57 SQLite docs specify setting the key immediately after opening and before other database operations; implementation follows that sequence. Native behavior remains unverified. |
| Blind: Logout/deactivation could race a draft deletion after authorization. | **medium, patch (fixed)** — Previously authorization and database deletion were not linearized. Story 5.2 now serializes protected draft operations with lock transitions; a test proves logout waits for an already-authorized delete and denies later reads. |
| Blind: accepting `online-authorized` might bypass server authorization. | **false** — App routes draft access through Story 5.2 `withProtectedAccess`, which evaluates the identity-bound local grant; online server access remains separately revalidated by existing App flow. |
| Blind: identical content unnecessarily increments revision. | **low, patch (fixed)** — Repository now returns the committed record unchanged when payload content is identical. |
| Blind: malformed negative/backward timestamps can pass parsing. | **low, patch (fixed)** — Parser rejects negative timestamps and `savedAt < createdAt`; saves keep timestamps monotonic. |
| Blind: SQLite update/revision behavior is not exercised by the test adapter. | **false** — Rendered tests call the production SQLite adapter against a deterministic transaction mock that applies the expected-revision upsert guard and rollback behavior; repository tests cover competing revisions. Native SQLCipher remains a separate unverified platform check. |
| Blind: migration fake does not roll back partial failure. | **false** — Migration test fake now restores version/statements on thrown migration and asserts that failed migration leaves prior state unchanged. |
| Blind: no eligibility guard prevents pending/submitted task drafts. | **false** — This story exposes the editor only from an assigned task detail or an existing account-bound local draft. Pending/submission lifecycle does not exist in this implementation and is explicitly out of scope. |
| Verification gap: delayed save can finish with stale content after a newer edit. | **medium, patch (fixed)** — Saves now track revision by account/task and re-read the active editor generation before acknowledgement, committing any newer edit. Rendered test delays a save, edits again, then verifies the newer value resumes after remount. |
| Edge: autosave skips the first edit because save state is idle. | **false** — The input handler sets save state to `saving` before the effect evaluates its guard; the rendered autosave test observes a committed acknowledgement. |
| Edge: queued save uses another task/account's revision after navigation. | **false** — Back navigation and sign-out flush saving edits before changing scope; revision tracking is now keyed by employee/task, and stale results cannot update another active scope. |
| Edge: logout while state is saved can drop a pending timer's changed content. | **false** — Any content edit changes save state to `saving`; sign-out flushes `saving` or `failed` edits before locking. A saved state has no newer unsaved edit. |
| Edge: back navigation drops an edit while autosave timer is pending. | **false** — Editing marks state `saving`; the back action awaits a durable save and stays on detail when it fails. |
| Edge: confirm-delete races a queued save and recreates/overwrites a draft. | **false** — Repository serialization plus revision-conditional DB save/delete means the stale operation fails instead of replacing a newer revision or recreating after delete. |
| Edge: resumed content could repopulate UI after authorization lock. | **false** — Reads execute under the same serialized Story 5.2 protected-access gate as logout/deactivation, so the lock transition cannot overtake an authorized read. |
| Edge: two repository instances could silently overwrite an initial record. | **false** — SQLite save is an exclusive transaction that checks the current revision before upsert; a second absent-revision insert sees the committed revision and fails. |
| Edge: deletion could remove a replacement draft after stale confirmation. | **false** — Delete SQL predicates on employee, task and expected revision and requires exactly one affected row. |
| Edge: missing SecureStore key and existing DB could destroy protected data. | **false** — Initialization never deletes/recreates the DB on failure; a failed new-key attempt removes only that temporary key and preserves encrypted file contents. |
| Edge: authorization could close between delete check and deletion. | **medium, patch (fixed)** — The previous check-operation-check sequence allowed a lock to interleave; `withProtectedAccess` now holds the authorization transition queue through the operation. |
| Edge: versioned DB could have an incomplete schema without detection. | **false** — Version 1 initialization verifies the `local_drafts` table explicitly and fails closed if it is absent. |
| Edge: successful delete provides no visible confirmation. | **low, patch (fixed)** — French `Brouillon local supprimé.` feedback is shown after durable deletion in both detail and list flows. |
