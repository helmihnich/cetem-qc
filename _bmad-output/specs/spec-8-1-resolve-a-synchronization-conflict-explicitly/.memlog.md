- (capability) CAP-1 Pause on conflict: once a conflict outcome is stored, no further item of that task is sent (automatic or explicit run) and Soumettre is unavailable until the conflict is resolved; other tasks keep syncing.
- (capability) CAP-2 Conflict view: the Employé sees the preserved local version (local revision, saved date, pending snapshot if any) and the current server version (revision, state, last change date and actor) fetched from the server, plus which form fields differ; a fetch failure is shown with a retry and no fabricated metadata.
- (capability) CAP-3 Keep local version: an explicit action creates, in one local transaction, a new sync-draft operation from the preserved local version, with the current server revision as base and sync-conflict-revision lineage to the conflicted operation; the task becomes an editable draft; the server stores the lineage when it accepts that revision.
- (capability) CAP-4 Discard local version and reload: after a confirmation explaining the loss, one local transaction replaces the local working version with the fetched server version, respecting its lifecycle (accepted evidence stays read-only), and records the resolution; conflicted and withdrawn snapshots stay preserved.
- (capability) CAP-5 Server support: GET current audit version for the assigned Employé; optional conflictOperationId on the sync envelope; insert-only sync-conflict-revision lineage row written in the acceptance transaction.
- (capability) CAP-6 Sync wiring extracted from App.tsx into a tested controller and hook before the conflict UI is added (epic-7 retro item 21), behaviour unchanged.
- (decision) Pause scope: an open conflict (conflict outcome item without a resolution record) stops its task in every run, explicit retry included; the engine also stops the task right after recording a conflict outcome. Resolves the 7.1 review deferral (later items with stale base).
- (decision) A draft conflict stays editable offline (OD-02b requires no lock for drafts; field work is offline-first): saves update the local draft only and create no sync-draft item while the conflict is open; Soumettre, delete and deleteUnreadable are refused. A submit conflict (or an unresolved submit behind a conflicted item) stays locked read-only (OD-02b step 1).
- (decision) Server version source: new GET /api/v1/employee/tasks/{taskId}/audit-version returns the current revision metadata and payload (null when no audit) to the assigned Employé (7.3 hand-off: latest audit_revisions row). Both resolution actions require a successful fetch in the current conflict view (OD-02b step 2: no fabricated metadata); the stored 409 metadata is shown offline, labelled as known at conflict time.
- (decision) Keep-local is not offered when the fetched server state is submitted: 7.4 refuses any new revision on accepted evidence. Only reload is offered, and the reloaded task shows « Soumis — accepté par le serveur », read-only (OD-02b step 5).
- (decision) The keep-local result is an editable draft with a queued sync-draft (base = fetched server revision, lineage to the newest open conflicted operation). It never re-queues a submission: the Employé submits again explicitly (AC « separately authorized sync attempt »; OD-02b steps 4–5).
- (decision) Withdrawn items: the task's unresolved items at resolution time (never attempted, guaranteed by the pause) are deleted from outbox_operations in the resolution transaction; their snapshots are kept and their IDs recorded in the resolution. Third explicit exception to the 7.1 preservation rule, next to explicit delete and supersession. Resolution is refused if any unresolved item of the task was attempted.
- (decision) Supersession keeps lineage: a save or submission that supersedes a never-attempted item carrying conflictOperationId inherits it, so the lineage reaches the server.
- (decision) Server lineage: migration 0011 audit_lineage_links (link_type CHECK sync-conflict-revision only; 8.2/8.3 extend it), FK to audit_revisions and to sync_operation_outcomes(operation_id), UNIQUE predecessor, insert-only and truncate-refused like 0009/0010. The reference must be a stored conflict outcome of the same actor and task, not yet linked; otherwise stored 422 rejected INVALID_CONFLICT_REFERENCE. Checked after the base-revision check, before payload validation.
- (decision) Fingerprint compatibility: conflictOperationId enters the request fingerprint only when present, so fingerprints of existing stored outcomes are unchanged.
- (decision) Local schema v4: outbox_operations gets conflict_operation_id; insert-only conflict_resolutions and conflict_resolution_items tables. Technical model; column names adjustable.
