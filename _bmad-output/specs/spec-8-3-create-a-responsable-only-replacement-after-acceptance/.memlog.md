- (capability) CAP-1 Show which own-team tasks have an accepted audit: the Responsable list shows « Soumis — accepté par le serveur » for a task whose audit is submitted, else « Brouillon ».
- (capability) CAP-2 Create a replacement control: Responsable-only explicit action « Créer un contrôle de remplacement » on an accepted, not yet replaced own-team task opens the normal task-creation form with the original link; one transaction creates the new task, its assignment and one immutable `replacement-control` link; the original is untouched; failure changes nothing.
- (capability) CAP-3 Replacement is independent: the new task is an ordinary draft task assigned through normal rules; its audit, measurements, timestamps, calculations and lifecycle start empty and follow 7.x/8.x unchanged; nothing is copied from the original.
- (capability) CAP-4 Reciprocal lineage: the list shows « Remplacement de l’audit X » on the replacement and « Remplacé par l’audit Y » on the original, derived only from the link table.
- (capability) CAP-5 Employé exclusion: no Employé route, response field or mobile UI exposes or invokes the replacement; an Employé call is refused 403 and writes nothing.
- (decision) Lineage storage: new insert-only table `audit_replacement_links` (migration 0013, owned by `audits`), link_type CHECK 'replacement-control'; columns original task/audit/accepted submission, replacement task, actor, created_at; UNIQUE original_task_id and UNIQUE replacement_task_id; CHECK distinct tasks; history-only and no-truncate triggers like 0011. Reason: audit_lineage_links requires a successor revision and a predecessor outcome that a replacement does not have; never reuse `sync-conflict-revision` or `rejected-submission-correction` (8.1/8.2 hand-offs).
- (decision) The replacement audit is created by the existing rule (first accepted sync of the replacement task, 0009); the link names the replacement task, which has at most one audit, so the link resolves to that audit. Creating an empty audit row is impossible (current_revision >= 1) and would break the 7.3 base-revision protocol. AD-4 « creates the new task, audit, assignment » is satisfied by the new audit identity being bound to the new task from creation.
- (decision) One replacement per original (UNIQUE original_task_id): UX copy names one successor (« Remplacé par l’audit Y ») and `button-primary` forbids duplicate outcomes from repeated requests. An accepted replacement is itself an accepted audit and may be replaced (chain). Technical cardinality, not a CETEM rule; revisable by a later migration.
- (decision) Identifiers in lineage labels are task IDs (the list's ID column); one task has exactly one audit, and the replacement audit does not exist before its first accepted sync.
- (decision) Normal task creation: same request body and rules as POST /tasks (establishment, service, graphie_mobile, active own-team assignee), empty form, nothing prefilled or copied (UX « No new copy-forward or transfer policy is inferred »). The original's assignee may be chosen, or another active one; a deactivated original assignee does not block the replacement.
- (decision) Entry point: W4/H1 do not exist yet, so the action sits on the W2 list row of an accepted, not yet replaced task. 9.1/Epic 11 may add the same action on their detail screens through the same route.
- (decision) API: POST /tasks/{taskId}/replacements, body CreateTaskRequest; 201 {task, replacementOf {taskId, auditId}}; 403 FORBIDDEN (non-Responsable, checked first); 404 TASK_NOT_FOUND (malformed, unknown or other team, indistinguishable); 400 VALIDATION_ERROR; 409 AUDIT_NOT_ACCEPTED; 409 REPLACEMENT_ALREADY_EXISTS; 422 TASK_ASSIGNEE_UNAVAILABLE; 500 INTERNAL_ERROR. Order: role, ID, body, then in one transaction: original own-team row FOR UPDATE, accepted submission, existing link, assignee FOR UPDATE, inserts. UNIQUE violation maps to 409 REPLACEMENT_ALREADY_EXISTS.
- (decision) Module split (AD-3): `audits/commands/create-replacement-control.ts` owns the command and the link insert; it calls a `tasks/commands/` function that inserts task + assignment on the given transaction client (extracted from createAssignedTask, which keeps its behaviour). The list's acceptance state and lineage come from an `audits/queries/` read composed in the route.
- (decision) TaskListItem: `state` enum [draft, submitted] (submitted = the task's audit state is submitted), required nullable `replacementOf` and `replacedBy` (task IDs). The original's tasks row, updated_at, audit and evidence are never written.
- (constraint) Never modify the original task, assignment, audit, revisions, submission, outcomes or lineage rows; no automatic status change on either record; no copy of measurements, comments, calculations or results.
- (constraint) Responsable-only, own-team only, server-enforced; denied requests disclose nothing; Employé never sees or calls the action.
- (constraint) OpenAPI first, generated types, zod schemas, typed client; French copy in packages/i18n; synthetic test names; PostgreSQL harness with zero skipped; no test deleted, skipped or weakened; gate scripts unchanged.
